Fadeno

A meta-harness for common subagent workflow patterns, neutral across harnesses and models. It routes work to models by role, wraps the spawn with deterministic scaffolding, and keeps a record nobody has to think about. Everything else is the intelligence's job.

This document specifies behaviour, not implementation. Every call in it has been made and reviewed; nothing is left open.

01What Fadeno is for

The user is someone constantly splitting and routing work between different models on different harnesses, who needs structure without ceremony. Fadeno gives them four things and deliberately nothing else:

  • Routing. Name a model once; point roles at it; change the binding at user, repo or session scope with one command.
  • Spawning. Launch subagents from inside a host session, on the right model, in a scaffolded environment.
  • Logging. A durable record of what was delegated, on what, and how it ended — written without anyone asking for it.
  • Context. The host knows how to use Fadeno; each subagent knows its own job.

Complex environment setup, merge judgment, conflict resolution and workflow structure are not Fadeno's work. They belong to the intelligence, which has context Fadeno cannot have.

02Ontology

archetype
A role you point at a model: worker, reviewer, judge, scout, director by default. The set is open — users define their own. Each carries a natural-language description that tells a director when to reach for it.
dial
The binding from an archetype to a model and effort, at user, repo or session scope. A dial may also point at another archetype, carrying its model and effort together.
harness
A coding agent Fadeno can work with. A host harness is one Fadeno can observe spawns inside; a driver harness is one Fadeno can launch as a process. A harness may be both.
lane
How a dispatch is delivered. Host lane: a subagent inside the caller's session. Command lane: a process Fadeno spawns. The lane is chosen by Fadeno and is invisible to the host.
dispatch
One unit of delegated work. Has a UUID, a semantic name, a worktree, and exactly one terminal decision.
worktree
A git worktree on its own branch, cut from HEAD or a named ref, where a dispatch does its work.
ledger
The append-only record at .fadeno/dispatches.jsonl. Three row types; nobody writes to it by hand.

03Routing

Resolution

  • An archetype resolves to a model and an effort, by walking the merged dial map across scopes — most specific scope wins per key.
  • A dial pointing at another archetype is followed to a terminal model. An alias carries model and effort together. Wanting the same model at a different effort means a separate route, not a partial alias.
  • Aliasing binds routing, never meaning: an aliased archetype keeps its own description.
  • Cycles are refused at set time and at resolve time — a cycle can be formed across scopes by two edits that are each individually valid.
  • An archetype with no dial resolves to current-host: the host session's own model. This has no edge case — no dial means no model, therefore no harness, therefore host lane.

Visibility

Routing is invisible by default. The host asks for an archetype; Fadeno resolves and applies model and effort without the host thinking about it. Two escape hatches exist and are not encouraged: fadeno dial resolve for inspection, and an explicit model override on a spawn — the real case being a director escalating a task that keeps failing.

Vocabulary is snapshotted; routing is live

This distinction governs when anything must be re-run, and it must not blur.

  • Descriptions are injected when a host session activates, so adding an archetype or editing a description requires re-activation. The CLI says so on those changes — and only those.
  • Dials are resolved at spawn time and are always current. Changing a dial requires nothing.
  • Fadeno stamps a catalog fingerprint at activation and reports staleness at the next spawn, so an ignored advisory or a teammate's edit still surfaces.

04Spawning

Fadeno wraps every spawn with deterministic scaffolding. On the host lane the wrapper is a hook; on the command lane it is the CLI itself. Both do the same four things.

The spawn wrapper

  1. Resolve the archetype to a model and effort, and apply them to the spawn.
  2. Choose the lane — host if the resolved model can be delivered in-session, command otherwise. The host is not told which.
  3. Cut a worktree on a branch, from HEAD or a named ref, and record its path, branch and base.
  4. Inject the worker's contract into the prompt, and write the opened row.

On the host lane the hook applies model and effort by rewriting the spawn. Where the resolved model can only be reached as a process, the hook instead redirects the spawn to a dispatch proxy — a minimal agent whose only job is to invoke the command lane. The host observes no difference.

The proxy is the design on every harness, not a fallback. A hook may turn out to be able to invoke the command lane directly on some harness; the design does not assume it, and does not vary by harness where it can. One path that works everywhere beats a faster path that works in one place — the same reasoning that put the worktree contract in the prompt rather than using Claude's native isolation.

The worktree

  • Cut from HEAD or a named ref — never from dirty state. Git cannot check out uncommitted work, and replaying it is complexity nobody needed: if a worker requires uncommitted work, the host commits first or requests a shared tree.
  • On a branch, named fadeno/<semantic-name>, so the ledger and git agree on one identifier and a forgotten dispatch is findable by git branch alone.
  • The command lane uses a worktree too, under the same rules — and more easily, since Fadeno sets the process's working directory directly.
  • If git worktree add fails, the spawn proceeds in the shared tree and the prompt says so. An environment problem must not cost a turn.
  • A shared tree remains available on request. When one is requested while another shared dispatch is open, say so — that is the only collision git does not solve.

Branch-name sanitization is deliberately dumb: lowercase, replace runs of anything outside [a-z0-9._-] with a single -, trim to 60 characters. A collision created by the trim is just another collision, handled by the duplicate counter that already exists. No cleverness, because a surprising branch name is worse than an ugly one.

05The three contracts

What the worker is told

  1. Its worktree path and branch, and that it should work there.
  2. That it owns the work: make the change, commit it, and before finalising, merge from upstream and resolve conflicts in its own tree — the responsibilities of a pull-request author.
  3. That its return message must state what is in the worktree, including anything untracked, and recommend whether it should be merged or discarded.

What the host is told

  1. The dispatch's UUID and semantic name, at spawn and again at stop where the harness allows.
  2. That the worker's report is a recommendation to weigh, not a finding to accept — read it and reach an independent conclusion.
  3. Every unclosed dispatch in this repository, at each spawn, with the insistence that they be reviewed and closed.

What closing requires

Exactly one verb: merged, kept, discarded, or failed, with an optional note. Fadeno performs no merge — the host does, or delegates it. The requirement is that the decision be made, not that Fadeno make it.

The nag

  • At every spawn, the host is reminded of all unclosed dispatches by UUID and name.
  • At five unclosed, the next spawn is refused until some are closed. Configurable; not exposed initially.
  • Scope is repository-wide, not session-wide. A director that spawns three workers and exits leaves dispatches with no owner; session scope would hide them permanently — exactly where nesting happens. Grandparents inherit orphans.
  • Reporting targets the stop hook where a harness supports it, and goes into the nag regardless. The nag is load-bearing; stop-time reporting only makes the news arrive sooner.
  • When a worker's working directory did not match its assigned worktree, say so — at stop and in the nag.

The threshold is configured in .fadeno/executors.yaml, alongside the dials — it is repo-scoped policy and that file is already the repo's Fadeno config. Wired from the start, unexposed until someone asks.

06Context delivery

  • A host session receives the archetype vocabulary and Fadeno's rules when it activates host mode.
  • A spawned director receives the same content injected into its prompt. A director never activates host mode, yet it is the archetype most needing the vocabulary — its job is choosing what to spawn next.
  • Both come from one source, so they cannot drift.
  • Injected content is the archetype list, routing behaviour, the worktree contract and the close obligation — not setup prose. General rule: if an intelligence can spawn, it needs the vocabulary.

07The ledger

Three row types, because "started", "the agent stopped" and "the host decided" are three facts, recorded by three parties, at three times. Nothing here is written by hand.

# opened — by the wrapper
id · name · at · session · parent · archetype · model · effort
explicit_model · lane · harness · workspace{path,branch,base} · task · prompt

# stopped — by the stop hook, an outside observation
id · at · final_message · dirty

# closed — when the host decides
id · at · verb · note
  • parent is load-bearing: without it, "which dispatches did this director open?" is unanswerable and orphan inheritance cannot be computed.
  • task holds the first ~300 characters of the caller's prompt, flagged when truncated. prompt points at the full text at .fadeno/prompts/<id>.md.
  • Prompts live outside local/ so clean cannot orphan the rows that reference them. They are evidence of what was asked, not scratch. Unbounded by design.
  • The log records what was asked, never what Fadeno injected — injected text is identical every time, so storing it would make the log describe Fadeno instead of the work.
  • final_message records presence, never completeness. On Claude's interrupted path the harness supplies no message at all, so its absence says nothing about whether work finished.

08Command surface

CommandDoes
dialShow, set and resolve archetype bindings. With no arguments, lists archetypes with descriptions and resolved models — the director's reference.
modelsInspect the registry; verify an alias actually resolves against its backend.
dispatchesList dispatches; show one; find output by UUID or name.
dispatch-closeRecord the terminal decision for a dispatch.
worktreesReport worktrees holding unmerged work. The cross-session safety net.
statusEffective routing, harness integration, and whether anything needs attention.
cleanRemove machine-local scratch — worktrees and outputs, never prompts or the ledger.
pluginGenerate the harness plugin from this checkout.
setupLink the CLI onto PATH. A symlink, never a copy — one copy makes version skew structurally impossible.
completionShell completion.

worktrees is its own verb rather than a section of status. It is the report someone runs deliberately when they suspect work was forgotten, and burying that in a status wall makes it easy to skim past — which is the exact failure it exists to catch.

09Non-goals

Named explicitly, because each was in the product and was removed for a reason. Anything here must argue its way back in.

Fadeno does not

  • Structure workflows. Playbooks, gates, run ledgers and repair loops are gone. A workflow is a sequence of dispatches, which the intelligence composes. They may return as a plugin above this layer.
  • Adjudicate models. No shadow pairs, no blinded judging, no bakeoff.
  • Enforce or attest. No prompt digests, no relay attestation, no tamper detection, no verify. The ledger records; it does not police.
  • Materialize agent files. Model and effort are set at spawn time. Nothing is written to ~/.codex/agents or .claude/agents, so nothing goes stale and no steering apply exists. Fadeno does report a hand-created agent file, because such a file silently overrides what a spawn passes.
  • Police concurrent writes. No window log, no overlap stamps, no lease, no lock. Worktrees and real merges remove the shared-tree world that machinery existed for.
  • Impose deadlines. Nothing Fadeno launches is killed on a timer.
  • Decide what work is worth keeping. It never destroys a worktree holding uncommitted work, and never judges whether output matters.
  • Diagnose itself. No doctor. With nothing materialized, no second CLI copy and no run ledgers, there is nothing to diagnose.

10Harness support

A harness is a host harness if Fadeno can observe spawns inside it — which in practice means Claude-or-Codex-compatible hooks. Everything else is a driver harness, reached through the command lane, which loses nothing: the command lane is where Fadeno controls the process outright.

HarnessHostDriverNote
claudeyesyesShips Node; hooks work out of the box
codexyesyesHook trust is a prerequisite for host use, and users must know it
ompyes—Reuses Claude-style hook manifests
grok, opencode, muse, agy—yesDriver-only

Fadeno remains an npm package. Six of seven harnesses ship no Node, so those users install a runtime their harness does not otherwise need — accepted for now, revisited if a real user objects.
